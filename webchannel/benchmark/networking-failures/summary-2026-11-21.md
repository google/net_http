# iOS networking-failure tests: HTTP/3 results and close-out (2026-11-21)

This summary follows the [2026-11-15 summary](summary-2026-11-15.md). It covers
the HTTP/3 runs ([2026-11-17](2026-11-17/report.md),
[2026-11-18 M6](2026-11-18/h3-m6-qlog/report.md)) and the HTTP/2 follow-ups
([2026-11-16](2026-11-16/report.md)). All runs used a physical iPhone SE (3rd
generation), iOS 27.2.1, with the AP wired directly (no Linux box in the path)
and an unchanged SDK.

## Status

run on HTTP/2 and on HTTP/3 (§9), using
`https://webchannel.googleapis.com/staging/channel/generator` for HTTP/3.

**Takeaways**

- **Recovery timing doesn't depend on the protocol.** Detection, give-up,
  pending-write and suspension results on HTTP/3 fall within the HTTP/2 ranges.
- **Session lifetime is about 120 s:** suspended sessions resumed when the last
  GET had started 112.9 s earlier, and failed at 128.3 s.
- **iOS often falls back to HTTP/2 during recovery:** 18 of 51 HTTP/3-started
  sequences used HTTP/2 after the fault.
- **Handoffs are smoother on HTTP/3:** the existing connection carried on, with
  no SDK-visible gap.
- **Early give-up when iOS reports the path as unsatisfied happens on the
  direct AP too** (HTTP/2 T5 at 93.5 s, HTTP/3 T3), so it isn't a
  test-topology artifact.
- **The default demo host `webchannel.sandbox.google.com` serves HTTP/2
  only.** Keep using the googleapis host for HTTP/3.
